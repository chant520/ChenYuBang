# OCR 样张实测记录（阻断项 1）

> 结论先说：**代理引擎 18/20 = 90.0% 通过**，达到方案里「≥90% 落地首选」的档。
> 但这不是 App 端侧引擎的实测数字——本机只有 Windows 自带的离线中文 OCR，没有 Android 机与 PaddleOCR 运行时。所以验收第 9 条仍标记「代理实测，待真机复测」。

## 一、测了什么

| 项 | 值 |
| --- | --- |
| 样张 | 20 张真实卷面照片 `docs/OCR-DEMO/1.PNG … 20.PNG` |

| 单张耗时 | P50 65 ms，P90 88 ms（桌面 CPU，不代表手机） |
| 原始数据 | `docs/OCR-DEMO/ocr-boxes/*.json`（词 + 坐标）、`results-boxes.json`（结构化结果）、`report-boxes.md` |
| 统计脚本 | `python tools/ocr_passrate.py docs/OCR-DEMO/results-boxes.json --target 0.9` → PASS |

## 三、两个失败是什么性质

- **8 号**：题干、A、B、D 都对，**C 行整行漏识**。照片本身五要素齐全（已目视核对）。
- **14 号**：A、D 对，**B、C 两行漏识**。照片本身五要素齐全（B 还是红字标注的答案）。

两张都是「整行丢失」，不是「整题读糊」。这类失败在 P19 里补两行字就能保存，不阻断流程——这正是产品把「手动补字」定为唯一兜底的场景。

## 四、一个必须写进工程的发现

同一张照片（1 号）：

- **原图直接识别**：把「高质量发展」读成「高质友展」，并且 C 行丢失；
- **2× 放大后再识别**：题干、A/B/C/D 全部正确。

结论：P18 裁切后不要直接把原尺寸图喂给引擎，**先按短边 ≥1400px 上采样**再识别。这条已写入 §2.3 的实施要求，不依赖具体引擎。

## 五、这个数字不能当验收数

限制逐条写明：

1. **引擎不同**。PaddleOCR / Vision 带方向分类与更细的检测框，对双列与倾斜通常更稳；Windows OCR 是另一套模型。
2. **没走 P18 人工裁切**，样本是整张截图/翻拍，裁切后的表现会变（通常更好）。
3. **没计拍照、IO、上采样耗时**，65ms 不代表手机端体验。
4. **样张难度维度没记录**：`样张登记表.csv` 里来源/光线/角度/干扰四列是空的，因此不能声称覆盖了偏暗、倾斜、双栏等维度。要补就补这四个字段，别补结果。

所以：验收第 9 条写「代理实测 18/20＝90%，App 端侧引擎待真机复测」，不写「90% 达标」。
