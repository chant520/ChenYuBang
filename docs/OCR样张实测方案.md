# OCR 样张实测方案（阻断项 1）

> 状态（2026-11-17 更新）：**代理实测已完成**——20 张样张在 Windows 离线 OCR 下 18/20＝90%，两张未通过均为整行漏识。结果、逐张表与限制见 `docs/OCR实测记录.md`；素材与本轮中间产物见 `docs/OCR-DEMO/README.md`。
> **仍欠一步**：App 端侧引擎（Android PaddleOCR mobile / iOS Vision）在真机上跑同一组 20 张，用该数字替换验收第 9 条的代理值。
> 以下「二、三」是样张与流程的原始口径，保持不变。

## 一、要量的是什么

产品验收第 9 条的一句话是「识别完整性」——落到可测口径就是：

> 一张卷面照片跑完 P17 → P18 → P19 后，**题干与 A/B/C/D 四个选项都被填进可编辑框**，算一条通过。
> 少任意一项（含题干被切成两段、选项文字粘到题干里）都算不通过。

不做「字段级准确率」：MVP 里用户可以在 P19 手动改，衡量的是「有没有给全」，不是「一个字都不错」。

## 二、样张怎么选（20 张，宁可难看也不要挑好看的）

| 维度 | 要求 |
| --- | --- |
| 来源 | 至少 3 种：印刷真题书、手机翻拍打印纸、截图/PDF 二次打印 |
| 光线 | 至少 4 张偏暗、2 张有阴影、1 张反光 |
| 角度 | 至少 5 张有明显透视倾斜（不是正对） |
| 版式 | 至少 3 张双栏；至少 2 张选项是横排一行（不是竖排） |
| 干扰 | 至少 2 张有手写批注、划线 |
| 分辨率 | 短边 ≥1080；允许 1 张低到 720（看下限） |

**不许做**：先把照片裁干净再喂算法；只挑正中、明亮、竖排选项的样张。那样量出来的通过率没有意义。

## 三、流程

1. 照片按 `P01…P20` 命名，放 `shared/fixtures/ocr/`（只在本机，不进包）。
2. 在 `shared/fixtures/ocr/样张登记表.csv` 里填每张的维度（来源/光线/角度/版式/干扰）。
3. 真机走一遍 P17→P19，把每张的识别结果导出成 `shared/fixtures/ocr/results.json`：

```json
[
  { "id": "P01", "stem": "……", "A": "……", "B": "……", "C": "……", "D": "……", "durationMs": 1830 }
]
```
   空字段写 `null`，不要用空串糊。

4. `python tools/ocr_passrate.py shared/fixtures/ocr/results.json --target 0.9`
   输出：逐张是否完整、完整率、耗时 P50/P90。

5. 数字回填两处：产品文档验收第 9 条、`docs/开发规范-v1.4.md` §11.3 第 9 行。

## 四、判据与不达标处置

- 通过率 **≥90%**：按首选方案（Android PaddleOCR mobile 内置模型 / iOS Vision `zh-Hans` + `.accurate`）落地。
- **80%–90%**：先做版式适配（双栏切分、选项行合并），复测一次；仍不达标换备选（Tesseract）。
- **<80%**：换引擎，并记录是「哪一类版式」掉下来的，写进 §15 风险表。
- 任何情况下都**不许**为了提通过率改成云端 OCR——那是新增第三处联网，产品口径明令禁止（§2.3）。

## 五、现在有什么数、还缺什么

已有：20 张真实样张跑了代理引擎，18/20＝90%（详见 `docs/OCR实测记录.md`），并发现一条工程约束——**送识别前必须把短边放大到 ≥1400px**，否则会整行丢字。

仍缺：真机 + App 引擎。本机没有 Android SDK / JDK 17 / PaddleOCR 运行时，也没有 Xcode，因此代理数字不能当作 App 的验收数，也不能用它下「换候选」的结论。
