# 角色隔离与提示词规范（全局 · 项目副本）

> 适用于本项目及所有 WorkBuddy 项目（Claw 除外）。目的：让每个项目的产品 / 开发 / 设计角色互相隔离、可复用、不串味。

## 一、目录分工（隔离的物理基础）
- 项目级角色：`<项目根>/.codebuddy/agents/<角色>.md` —— 本项目专属，各项目各存一份。
- 项目级规范：`<项目根>/.codebuddy/AGENT-SPEC.md` —— 本规范副本（就是本文件）。
- 全局级：`~/.workbuddy/agents/` —— 仅放跨项目通用角色，**不写任何项目约定**。
- 判定口径：这段提示词是否只对本项目成立？是 → 放项目内；换项目也一字不改 → 才可进全局。
- 同名角色在不同项目里内容独立，路径不同即天然隔离，谁也读不到谁。

## 二、标准角色
- `product-dog`（产品）：需求分析、可行性调研、功能边界、验收标准，不写代码。
- `dev-super`（开发）：编码实现与技术验证。
- `designer-ui`（设计）：视觉方案与设计规范，不写实现代码。
- 扩展角色（如 audio-advisor）按项目需要新增，同样放本项目目录。

## 三、单个角色文件结构（六段式）
1. frontmatter：`name` / `description`（name 必须与派发时使用的 name 一致）。
2. 身份与职责边界。
3. 项目硬约定 —— **只写本项目的东西，这是隔离的核心**。
4. 工作流程 / 输出格式。
5. 禁止事项 —— 与其他角色划清边界。
6. 与用户交互 —— 重大决定上交用户拍板，不替用户选。

## 四、派发规则
- 一个角色一个唯一 name，同角色**串行**派发，完成回报后再派下一个。
- 确需并发：改用内置 `general-purpose`，并在 prompt 开头强制要求「先读取并严格遵守 `.codebuddy/agents/<角色>.md`」。
- 续做要用 `resume` + **原 name**，不要改名（改名 = 新会话，历史全丢）。
- 派发 prompt 必须**自包含**：项目背景 + 输入 + 任务 + 输出格式 + 约束，一次写全。
- 主控只做：拆任务 → 派发 → 审查产出 → 汇报用户 → 用户拍板后回传角色。
- **派发 prompt 末尾必须原样追加「输出纪律」段**（任何 subagent_type 无例外，含 general-purpose / Explore）：只回结论 / 改动清单 / 待拍板项，≤10 行或 ≤300 字；只用短行列表，每行「动词+对象+结果」；禁段落 / 总结段 / 复述 / 大段代码日志 / 思考过程 / 客套自评寒暄；禁英文 Here's/Let me/I've/In summary/Overall/Feel free/Note that/Additionally/However/As requested 与中文 好的/我来/综上/总之/希望有帮助/如需/值得一提的是；强制简体中文，仅用户明确要英文时才用英文；过程材料写文件正文只给路径；超限主控打回重写。子代理回复不达标先打回重写再给用户。

## 五、跨项目通用硬约定
- 图标一律内联 SVG 矢量图标，不用 emoji。
- 不写方案对比 / 代价推演 / 推荐 / 待定项分析；重大取舍交用户拍板。
- 需要拍板的多选用弹框卡片，互相关联的问题合并成一题。
- 工作日志追加到 `.workbuddy/memory/YYYY-MM-DD.md`（append-only）。

## 六、要避免的坑（本规范存在的理由）
- 角色定义缺失 → 派发时临时拼设定，质量不稳、难复用。
- 续做时换了 name → 变成新会话，之前产出全部丢失。
- 角色文件误写进别的项目的约定 → 隔离破裂、串味。

## 七、交付与验证流程约束（2026-11-24，跨项目通用）
- 交付前静态检查：开发 / 架构成员交活前自跑本平台静态检查（Android `ktlintCheck` + `detekt`；iOS SwiftLint + build）与定向单测，红灯不出手；回传命令、退出码与结果。
- 红灯分层：静态违规由实现方定向修复并复核，不触发全量门禁；全量门禁只在代码冻结后由 QA 跑一次。
- 证据一次定稿：日志一次归档（重定向或 tee），不覆盖后恢复；最终 head 与证据编号在汇编时一次定稿，不做反复修正提交。
- 主控只读结论：长文档 Grep 定位后按行段读，源码交给子代理读并回摘要；主控不亲自通读实现文件。
- 查询一次即停：检索无匹配即停止并请用户补充对象，不翻历史记录兜圈；关联拍板合并一题问完。
